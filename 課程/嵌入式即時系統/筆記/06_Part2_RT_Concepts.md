## 多工（Multitasking）

---

**多工（Multitasking）**是指 CPU 透過快速切換，讓多個任務看似同時執行的技術。uC/OS-II 採用優先權搶占式排程，確保就緒列表中最高優先權的任務永遠率先佔用 CPU。

### 任務的四大組成要素

每個任務由四個部分構成：

- **任務程式碼（Task Code）**：執行特定功能的 C 函式，必須以無限迴圈（`for(;;)` 或 `while(1)`）形式撰寫，不可自行返回（return），否則會造成未定義行為。
- **任務優先權（Priority）**：0 到 63 共 64 個等級，數字越小優先權越高；62 保留給統計任務（Stat Task），63 保留給閒置任務（Idle Task）。
- **任務堆疊（Stack）**：每個任務擁有獨立的堆疊空間，用於儲存局部變數與情境切換時的暫存器內容；大小需根據最深呼叫路徑手動估算。
- **任務控制區塊（TCB, Task Control Block）**：核心為每個任務維護的資料結構，記錄任務的優先權、狀態、堆疊指標、等待條件等所有執行資訊。

## 任務狀態機（Task States）

---

uC/OS-II 定義五種任務狀態，核心透過特定 API 呼叫驅動狀態轉換。

### 五大狀態定義

| 狀態 | 說明 |
|------|------|
| **Dormant（休眠）** | 任務程式碼存在於記憶體中，但尚未向核心註冊，不參與排程 |
| **Ready（就緒）** | 已向核心註冊，正等待 CPU 執行，位於就緒列表中 |
| **Running（執行中）** | 目前佔用 CPU 的任務；單核心系統中同一時間只有一個任務處於此狀態 |
| **Waiting（等待中）** | 正在等待某事件（計時到期、旗號、訊息等），不佔用 CPU |
| **ISR Running** | CPU 正在執行中斷服務常式，被中斷的任務暫時停止 |

### 狀態轉換 API 對照

- **Dormant 進入 Ready**：呼叫 `OSTaskCreate()` 或 `OSTaskCreateExt()`，將任務加入核心管理。
- **Ready 進入 Running**：排程器選出最高優先權就緒任務後執行情境切換。
- **Running 進入 Waiting**：呼叫 `OSTimeDly()`、`OSSemPend()`、`OSMboxPend()`、`OSQPend()` 等 pending 類 API。
- **Waiting 進入 Ready**：等待條件滿足（計時到期、旗號釋放、訊息抵達），核心將任務移回就緒列表。
- **Running 進入 Dormant**：呼叫 `OSTaskDel()`，將任務從核心移除。
- **Running 進入 ISR Running**：發生硬體中斷，CPU 跳至 ISR；原任務被暫停。
- **ISR Running 結束後**：ISR 呼叫 `OSIntExit()`，核心重新評估排程，可能喚醒更高優先權的就緒任務。

## 情境切換（Context Switch）

---

**情境切換（Context Switch）**是指儲存當前任務的 CPU 暫存器狀態（即「情境」），並載入下一個任務的情境，使核心得以切換執行中的任務。

### 切換成本與現代 CPU 惡化因素

- **基本成本**：儲存與還原所有 CPU 暫存器（通用暫存器、程式計數器、旗標暫存器等）所需的時脈週期。
- **現代 CPU 的額外惡化**：現代處理器具備深層管線（pipeline）、分支預測（branch prediction）與快取（cache）；情境切換後這些機制的預熱狀態（warm state）全部失效，需要重新填充，實際切換代價遠超過暫存器存取本身。
- **設計含義**：過度頻繁的情境切換會顯著降低系統整體吞吐量；任務切換頻率應與實際工作負載相符，避免過度細分任務粒度。

## 核心類型（Kernel Types）

---

核心類型決定 ISR 結束後 CPU 控制權的歸屬，直接影響即時回應能力。

### 不可搶占核心（Non-Preemptive Kernel）

- **定義**：ISR 完成後，CPU 控制權回到被中斷的原任務，而非排程器。
- **問題**：若 ISR 喚醒了更高優先權的任務，該任務必須等到原任務主動放棄 CPU（呼叫 blocking API），才能獲得執行機會，無法保證即時回應。
- **適用場景**：對即時性要求不高的系統，或不需要任務搶占的簡單應用。

### 可搶占核心（Preemptive Kernel）

- **定義**：ISR 結束時，排程器立即評估就緒列表；若有更高優先權的任務就緒，直接執行情境切換。
- **優點**：可保證系統對最高優先權任務的回應時間具有確定性（deterministic）上界，滿足硬性即時（hard real-time）需求。
- **uC/OS-II 的實作**：屬於完全可搶占核心；`OSIntExit()` 在每次 ISR 結束時觸發排程評估，確保最高優先權任務即時執行。

## 中斷處理（Interrupt Handling）

---

### ISR 執行流程（七步驟）

以非搶占核心的標準 ISR 流程為例：

1. **硬體觸發**：外部裝置發出中斷訊號，CPU 完成當前指令。
2. **儲存基本情境**：CPU 自動將程式計數器（PC）與旗標暫存器（PSW）壓入堆疊。
3. **查詢中斷向量表（IVT）**：CPU 依中斷號碼跳至對應的 ISR 入口位址。
4. **儲存額外暫存器**：ISR 手動保存其他需要使用的通用暫存器。
5. **執行事件處理**：ISR 讀取裝置狀態、發布旗號或訊息，通知等待中的任務。
6. **還原暫存器**：還原第 4 步儲存的暫存器。
7. **執行 `IRET`**：CPU 自動還原 PC 與 PSW，恢復被中斷的執行流。

在可搶占核心中，步驟 5 與 6 之間需插入 `OSIntExit()` 呼叫，讓核心評估是否需要觸發情境切換。

### 中斷延遲公式

**中斷延遲（Interrupt Latency）**定義為從硬體觸發中斷到 ISR 執行第一條指令之間的時間：

$$T_{latency} = T_{interrupt\text{-}disable\text{-}max} + T_{IVT\text{-}lookup}$$

- **決定性因素**：核心在臨界區（critical section）關閉中斷的最長持續時間（`OS_ENTER_CRITICAL` 至 `OS_EXIT_CRITICAL`）直接決定延遲下限；此段時間越短，系統即時性越好。

### 中斷計時三指標（Latency / Response / Recovery）

| 指標 | 定義 |
|------|------|
| **Interrupt Latency（中斷延遲）** | 中斷觸發到 ISR 開始執行第一條指令的時間 |
| **Interrupt Response（中斷回應）** | 中斷觸發到系統開始實際處理事件的總時間（含 ISR 前置暫存器保存） |
| **Interrupt Recovery（中斷恢復）** | ISR 結束後，系統恢復排程並切換至最高優先權就緒任務所需的時間 |

在可搶占核心中，Recovery 包含兩條路徑：

- **路徑 A**：ISR 未喚醒更高優先權任務，直接恢復被中斷的原任務（成本較低）。
- **路徑 B**：ISR 喚醒更高優先權任務，觸發情境切換後才恢復執行（成本較高，但確保即時性）。

### 巢狀中斷（Nested Interrupts）

- **定義**：允許高優先權中斷在低優先權 ISR 執行期間搶占 CPU，形成多層 ISR 巢狀。
- **計數追蹤**：uC/OS-II 以 `OSIntNesting` 計數器追蹤目前的巢狀深度；`OSIntExit()` 僅在計數歸零時才執行排程評估，避免在巢狀過程中提前切換任務。
- **堆疊需求**：每層巢狀中斷均需儲存情境，記憶體規劃時須乘以最大巢狀層數（見記憶體需求估算）。

### ISR 設計最佳實踐

- **保持 ISR 簡短**：ISR 應只執行最小必要工作（讀取狀態、更新旗號、發送訊息），避免在 ISR 內執行耗時運算，以壓低中斷延遲。
- **延遲繁重工作**：將需要長時間處理的邏輯移至專用的工作任務（worker task），由 ISR 發布旗號或訊息通知該任務。
- **禁止呼叫 blocking API**：ISR 中不可呼叫任何可能使任務等待的 API（如 `OSSemPend()`、`OSTimeDly()`），否則會造成死鎖或非預期的排程延遲。

## 時鐘節拍（Clock Tick）

---

**時鐘節拍（Clock Tick）**是 uC/OS-II 的系統心跳，由硬體定時器以固定頻率產生中斷，每次中斷觸發 `OSTimeTick()` 掃描所有 TCB 並更新延遲計數器。

- **典型頻率**：10–1000 Hz，最常見為 100 Hz（每 10 ms 一次）；頻率越高，時間解析度越好，但 ISR 開銷也越大。
- **核心功能**：將延遲計數到期的任務從等待狀態移回就緒列表，驅動 `OSTimeDly()` 等計時類 API 的到期機制。
- **啟動順序注意**：時鐘節拍硬體中斷必須在 `OSStart()` 啟動排程器之後才能開啟；若在核心初始化完成前觸發 `OSTimeTick()`，會存取尚未建立的資料結構，導致未定義行為。

---

## `OSTimeDly()` 的時間不精確性

---

`OSTimeDly(n)` 讓任務延遲 $n$ 個時鐘節拍，但實際延遲時間可能與名義值存在偏差，來源有三：

- **高優先權任務搶占**：延遲到期後，若有更高優先權任務正在就緒，呼叫 `OSTimeDly()` 的任務無法立即取得 CPU，必須等待高優先權任務主動釋放後才能繼續執行。
- **ISR 執行時間**：時鐘節拍 ISR 本身消耗時間，這段時間不計入節拍週期，導致實際等待時間略長。
- **節拍的離散性**：呼叫 `OSTimeDly()` 的時機可能落在節拍週期中間；若在下一個節拍即將到來前才呼叫，第一個節拍幾乎立即到期，導致總延遲比名義值少最多一個完整節拍。

實際延遲範圍估算：

$$( n-1 ) \cdot T_{tick} \leq T_{actual} \leq ( n+1 ) \cdot T_{tick}$$

若對時間精度有嚴格要求，應使用硬體計時器（hardware timer）直接觸發事件，而非依賴 `OSTimeDly()`。

## 記憶體需求估算

---

uC/OS-II 系統的總 RAM 需求由以下部分構成：

$$\text{RAM}_{total} = \text{RAM}_{app} + \text{RAM}_{kernel} + \sum_{i=1}^{N}\text{Stack}_{task_i} + \text{Stack}_{ISR} \times n_{nesting}$$

| 項目 | 說明 |
|------|------|
| $\text{RAM}_{app}$ | 應用程式的全域變數與靜態資料 |
| $\text{RAM}_{kernel}$ | 核心資料結構（TCB 陣列、就緒列表、事件控制區塊等） |
| $\sum\text{Stack}_{task_i}$ | 所有 $N$ 個任務各自堆疊大小的總和 |
| $\text{Stack}_{ISR} \times n_{nesting}$ | 支援巢狀中斷所需的堆疊，依最大巢狀層數計算 |

- **堆疊估算方式**：以最深呼叫路徑（deepest call path）中所有函式的局部變數總和加上情境切換所需的暫存器空間估算；uC/OS-II 提供 `OSTaskStkChk()` API 在執行時期監控實際堆疊使用量。
- **實務建議**：初期可預留 50% 的裕量，再透過執行期監控工具收斂到合理大小。
